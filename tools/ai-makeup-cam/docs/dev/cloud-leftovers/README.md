# クラウド側の残り物（cloud leftovers）

クラウドのセッションで、push していなかったもの**すべて**です（顔の画像・動画は含めていません）。
ブランチ `claude/wip-phase2`（8cde5db）の上に、このフォルダだけを足しています。

## 中身

| パス | 内容 |
|---|---|
| `scratch-scripts/<担当>/` | 第1弾と第2弾の各エージェントが、見た目の調整・性能測定・デバッグに使った使い捨てのスクリプト。担当：geometry, tracking, gui, skin, lips_blush, eyes_brows, hair, integrator, teeth, contour。`root/` は最初の動作確認用。パスはクラウドの `/tmp/claude-0/.../scratchpad/...` を前提にしているので、そのままでは動かない。手法の参考用 |
| `reports/phase1-agent-reports.json` | 第1弾の 9 エージェントの最終レポート（設計の判断、API の追加・逸脱、性能の実測、未解決の問題）。HANDOFF.md の「既知の問題」の元データ |

特に役に立ちそうなもの：
- `scratch-scripts/teeth/temporal.py`, `run_clip.py`：CREMA-D のクリップで、歯の効果をフレームごとに当てて統計と前後比較の帯画像を作るハーネス
- `scratch-scripts/contour/harness.py`, `looks.py`, `clips.py`：立体感・涙袋の見た目の比較（skin only / default / x2 / max）
- `scratch-scripts/integrator/gallery.py`, `make_presets.py`, `bench.py`：プリセットのギャラリー、プリセット生成、全体のベンチマーク
- `scratch-scripts/tracking/probe_jitter.py`, `sweep.py`：顔追跡のジッター測定、平滑化パラメータの掃引

## 歯のテスト 2 件の失敗（クラウド側で検証済み）

担当エージェントはテストを書いた直後に停止したので、原因の分析は残っていません。クラウド側で検証した結果：

1. `test_changes_stay_in_the_mouth_opening`（最大差 0.00296）
   - **主な原因はテスト側**。「外側」の判定に使っている `regions.expand_polygon(LIPS_INNER, reach)` は、
     各頂点を**重心から放射状に**動かすだけで、本当の意味での「輪郭から reach px 外側」になっていない。
     平たい口の形だと、**口角に近い上下の縁**ではほとんど広がらない。
   - 最大差の画素は、内唇の輪郭から**本当の距離で 3.0 px**（reach = 6.19 px の内側）、
     口の中心から (dx, dy) = (−25, −9) の、口角寄りの上側。つまり、ぼかしの正当な範囲内。
   - 距離変換で作った**本当のオフセット**（輪郭から 6.19 px より外側）で測ると、最大差は **4.2e-6** だけ。
     これはガウシアンの裾。OpenCV の float 画像の GaussianBlur は、カーネルが約 ±4σ まで広がる
     （`_FEATHER_REACH = 3.0` の想定より長い）ことと、すき間を埋める処理のカーネル（この顔で 3 px）の分。
   - 直し方の案：テストの「外側」を距離変換によるオフセットにする。さらに「外側は厳密に 0」を保証したいなら、
     効果の側で、最後に**支持範囲のマスク**（内唇の多角形を margin だけ膨らませたもの）を掛けるか、
     GaussianBlur に明示的な `ksize = 2*ceil(3σ)+1` を渡す。
2. `test_close_up_faces_are_processed_at_reduced_resolution`（最大差 2.5e-5）
   - 同じく `expand_polygon` で「外側」を作っている。加えて、縮小処理（`_MAX_WORK_SCALE`）で計算した差分を
     `INTER_LINEAR` で拡大して戻すので、裾が 1〜2 px 広がる。**こちらは数値を確かめていない**が、同じ直し方で解決する見込み。

ローカルの推測（「マスクのぼかしが想定範囲の外へわずかに漏れている」）は、半分正解です。
大きいほうの差（0.003）の主因は、テストの「外側」の作り方です。

## contour の初期値を 0.15 → 0.35 に上げた件

- エージェントは理由を書き残していない。作業記録から分かること：
  1 回目のレンダー（v1：0.15）を見た直後の 1 回の編集で、(a) フェイスラインの帯を細くする
  （"broad" の幅 0.05/0.11 → 0.04/0.09、jawline のストロークの座標を変更）、(b) shading と highlight の初期値を
  0.35 に上げる、を同時に行っている。
- クラウド側でレンダーを見て判断した内容：
  - **v1（初期値 0.15）**：「skin only」と「default」の差がほとんど見えない（静止画・動画とも）。
    **初期値では効いていない**と判断したと思われる。
  - **v1 の max**：1029（アフリカ系、濃い肌、中立の表情で話す場面）で、頬に横長の**明るい面**が広く出て、
    まだらに見える。→ 帯の幅を絞る理由になったと思われる。
  - **v3（初期値 0.35、最新）**：
    - 1074（アフリカ系、濃い肌、中立の表情で話す場面）：default は控えめで自然。x2/max で鼻筋のハイライト、
      頬の下の影が見える。**灰色っぽくはなっていない**が、大きな問題はない。
    - 1072（アジア系、明るい肌、口を開けて話す場面）：max で頬・おでこが平坦に明るくなり、
      **顔が白く平たく（お面っぽく）**見える。フェイスラインの影は弱い。
    - 1002（白人、とても明るい肌、話す場面）：x2/max で**鼻筋のハイライトが縦の白い線**としてはっきり出て、
      おでこの中央も白っぽい塊になる。人工的。ノーズシャドウの線も見える。
    - 1013（ヒスパニック系、中間の肌、歯を見せて笑う場面）：max で頬骨の下の影が斜めの暗い帯として見える。
      おでこの生え際にも影。強めの設定としてはぎりぎり許容範囲。
  - **未解決**：0.35 にしたあと、default の自然さの再確認をしていない。
    明るい肌でハイライトが強すぎる（線・塊になる）。テストなし。時間方向の安定性は未確認。
    最後は性能のための書き直し（係数を粗いグリッドで計算、ストロークの描画をまとめる）の途中で停止した
    （停止時のファイルは構文的には正しいが、書き直しが完了しているかは未確認）。
- **涙袋**（v1、性能の書き直し前）：
  - 1074（濃い肌、中立）：strong/max で下まつげの下の明るい帯が見える。max ではやや**白っぽい三日月**に見える。
  - 1002（明るい肌、笑顔）：自然。
  - 1076（白人、目を細めた・まばたきに近い場面）：max で下の影の線が目立つ。

## 会話で決まったことで、HANDOFF.md に書いていないこと

- **面接の時期**：会話に出ていない（不明）。
- **使う予定のカメラ**：会話に出ていない。今回、ローカルに Web カメラがないことが分かった。
  候補：USB の Web カメラを買う、Windows 11 の「スマートフォン連携」で Android スマホをカメラにする、
  Camo / DroidCam / Iriun などのアプリ。カメラがない間は、**動画ファイルをカメラの代わりに流すモード**
  （`--video` 入力や、カメラの選択肢に「動画ファイル」）を作ると、実機に近い確認ができる。
- **PC**：Ryzen 7 9800X3D（8 コア／16 スレッド）、DDR5 32 GB、RX 9070 XT（16 GB）。
  面接の本番中は開発用のエージェントを止める（CPU を使い切ってフレームレートが落ちるのを防ぐ）よう伝えてある。
- **使い方の前提**：対面の面接では本物のしっかりメイクをする。オンラインはメイクが面倒なので、
  アプリで**対面と同じ見た目**にしたい。そのため**案A の優先度を上げた**（基本アプリの次）。
  HANDOFF.md の順番（実機 → 第2弾 → 案A）と、会話の「案A を最優先」の両方があるので、本人に確認するとよい。
- **顔の形の補正**：目・鼻・口、輪郭・あご、涙袋、シェーディング・ハイライトを**全部入れたい**。
  理由は「顔採用が現実にある」から。夢は「整形と同じ効果」。
  → 方針：メイク系（立体感・涙袋）はしっかりめ、ワープは控えめ。ただし最終的な強さは本人がスライダーで決める。
  プリセット「しっかりメイク＋小顔補正（strong）」を作る予定。
- **強めの加工**：「強めの置き換えやメイクもやらないと」とのこと → strong プリセットと、案B の強さスライダー
  （「メイク寄り」→「ほぼ理想の自分に置き換え」）で対応する方針。
- **髪型**：アホ毛消し・シルエット、**前髪の変更**、**長さ・髪型ごとの変更**を希望（「就活向けのまとめ髪風」は選ばなかった）。
  髪型ごとの変更は、使うかどうかは分からないとのこと。段階は ①アホ毛・シルエット＋背景の撮影
  → ②自分の写真から切り抜いた髪型素材を重ねる（前髪を足すのは易しく、なくすのは難しい）→ ③3D。
- **歯**：ホワイトニングと色ムラ・影をなじませる、の 2 つ。**歯並び（形）を変えるのは、アプリ本体では作らない**
  （崩れやすく、ディープフェイク検知が口元を重点的に見るため）。案B の実験枠として、練習・自己確認用に限る方針。
- **3D モデルの発注**：本人が、雇った制作者に発注する予定。**まだ発注していない**。
  仕様書は `docs/3d-model-commission-spec.md`（髪型のオプションも追記済み）。
  「歯だけ先に発注」する案も伝えてある。
- **案B**：A と B の**両方**を採用する。学習は vast.ai で A100/H100 を借りる（大きい先生モデル → 蒸留）、
  実行は手元の RX 9070 XT（ONNX Runtime + DirectML）。クラウドでのリアルタイム実行は、口と声のずれ・回線の
  リスクがあるので**おすすめしない**と伝えてある。顔の丸ごと差し替え（DeepFaceLive 系）は、
  「技術的には作れるが、面接の本番では崩れのリスク」と伝えたうえで、強さスライダーの上限を
  評価の合格ラインで決める方針で合意。優先度は案A・第2弾より後。
- **面接の実態**：これまでの面接は全部 Zoom / Teams / Google Meet。「横を向いて」「手を振って」と
  頼まれたことは一度もない（日本の新卒の就活では一般的ではない）。手を挙げるような大きな動きはしない前提。
- **撮影**：`docs/capture-guide.md` の写真（メイク・すっぴん・髪型・背景）は、**次にメイクする日に撮る**
  と伝えてある。まだ撮っていない。
- **GitHub**：Claude の GitHub 連携は Rimcat-JA。FidesTherese 側のリポジトリには push できない。
